前几天翻了翻 BSOD-MEMZ 的个人网站，看完有个很直观的感受：我们俩做的都是"个人站"，但其实是两种完全不同的东西。他那边是纯手工的静态页面，我这边是 Nuxt 静态生成。表面上交付物差不多——都是一堆能被浏览器直接打开的页面——内的维护逻辑却是两套世界。

这篇文章不谈谁好谁坏，只谈差别，以及我为什么最终走到了 Nuxt 这条路。

## 一、两种架构的差别在哪

先说 BSOD-MEMZ 那个站。它是典型的纯静态结构：顶层十几个 HTML 文件，配一堆 CSS、JS、图片，还有 articles、projects、music 这些分类目录，每个页面一个独立的 HTML。没有构建步骤，没有框架，也没有内容管理系统——写新文章，就照着旧页面的结构复制一份 HTML，改标题、改正文、改日期；想换个导航，就得把十几个页面挨个打开改一遍。主题切换靠一段内联脚本读 localStorage、再用 document.write 注入不同的样式表，站点跳转靠一个 _redirects 文件做 301。仓库里只有一次提交，像是把整个目录一次性传上去的快照。

这套做法有个很大的优点：简单、透明、不依赖任何工具链。双击 index.html 就能看，扔到任何一个静态托管上都能跑，十年后也不会因为依赖过期而构建失败。对只想安安静静放几个页面的人来说，这是最省心的方案。

我这边则完全是另一套逻辑。站点由 Nuxt 4 驱动，内容源是 Markdown，组件从 Nuxt UI 取，样式用 Tailwind 的设计令牌统一管理，构建时一次性预渲染成静态产物，再部署到 Cloudflare Workers。想写一篇文章，我只需要在 content 目录下丢一个 Markdown 文件，归档、分类、标签、搜索、网站地图、上一篇下一篇这些全都自动生成，不用碰任何 HTML。

差别归结成一句话：**纯静态站维护的是"页面"，Nuxt 站维护的是"内容和数据"，页面由框架生成。**前者每加一个功能都要手工同步到每个页面，后者改一次数据源全站生效。竞技场里类比，纯静态像是每个技能都要手动瞄准、手动计算落点；Nuxt 像是把锁定和预判交给系统，我只需要下达指令。

## 二、我走过的弯路

我并不是一开始就站在 Nuxt 上的。恰恰相反，我是被纯静态站折腾够了，才一步一步挪过来的。

最早我也写过纯手工的静态页面。短期很爽——打开编辑器就能写，改完刷新就能看。但站点一长大，问题就来了：文章多了以后，列表页要手工维护；导航改一次，所有页面跟着改；样式想统一换个配色，得翻遍每一个文件；一篇文章的封面、摘要、日期、标签分散在不同地方，改一处漏三处是常态。更要命的是，这些重复劳动不产生任何新价值，纯粹是在跟结构本身搏斗。那种感觉就像法师位被逼着去平A——不是打不了，是每一分力气都花在了不该花的地方。

第一次突围是换到 Vue3 SPA。组件化把重复的结构收拢起来，导航、卡片、页脚各写一次全站复用，数据驱动渲染，手工同步的问题一下解决了大半。但 SPA 很快暴露了新问题：首屏要等 JS 加载，搜索引擎抓取不友好，对内容站来说这是硬伤——文章写得再好，搜不到就等于没写。

于是第二次换到 VitePress。它把静态生成和 Markdown 内容管理打包解决，首屏是现成的 HTML，SEO 也友好，写文章回归到纯文本。这一阶段其实很舒服，问题在于 VitePress 的定位是文档生成器：当你想要评论区、复杂搜索、自定义交互状态的时候，它就开始跟你对着干——这些东西文档生成器从设计上就没打算支持。

第三次，也就是最近这次，换到 Nuxt 4。它相当于把前面几代的优点合并：既有静态生成的首屏和 SEO，又有完整应用框架的能力，Markdown 内容库、组件体系、类型安全、设计令牌一次到位。回头看这条路——纯静态、Vue3 SPA、VitePress、Nuxt——每一步都不是赶时髦，而是被前一步的天花板顶着往前走。是痛点了才换，不是换了才找痛点。

## 三、Nuxt 的维护其实没那么难

在动手之前，我对 Nuxt 是有偏见的：框架大、概念多、构建链复杂，总觉得维护起来会很重。真跑起来之后，我发现这个判断错了。

难的是"选"，不是"养"。选型阶段要权衡架构、迁移路径、部署方式，确实费脑子；但一旦搭好，日常维护反而比纯静态还轻。写文章只是往内容目录丢 Markdown，版式、样式、SEO 全由框架兜底；改一个设计令牌，全站跟着变；想加一个区块，写个组件挂上去就行。以前在纯静态站里要改十几个文件的活，现在改一处数据源就够了。

构建期的校验和自动化也帮了大忙。站点地图自动生成，产物生成完逐条对账，静态预设、字体灌注这些约束都写进了流水线——以前要靠人肉记住的检查项，现在交给脚本，发布前自动挡一道。部署迁到 Cloudflare Workers 后，连缓存、跨域、404 回退都是默认行为，不用再一层层手动配。这些东西单看都很小，叠在一起，把"维护"从一件需要时刻盯着的事，变成了一件可以放心交给流程的事。

当然，Nuxt 不是没有代价。它引入了依赖，需要构建，本地要先装环境——这些对纯静态站来说都是"额外负担"。但这份负担是一次性的：装好、配好之后，它换回的是长期的省心。反观纯静态站，表面上是"零维护成本"，实际上是把成本摊到了每一次手工修改里，积少成多，一点不比框架轻。

所以我的结论是：别被"框架重"的表象吓住。对内容型站点来说，真正重的从来不是框架，而是那些不得不重复的手工劳动。Nuxt 把这些劳动接了过去，维护自然就变轻了。竞技场里选装备也是这个道理——看着沉的装备，往往才是让你活得更久的那件。

## 结语

BSOD-MEMZ 那个站和我的站，没有高低之分，只是取舍不同。纯静态换来的是极致的简单和长久的可用，代价是手工同步；Nuxt 换来的是内容驱动和自动化，代价是引入工具链。哪个更适合，取决于你的站要长成什么样。

对我而言，这一路走下来最大的收获，不是终于用上了"更先进"的技术，而是搞清楚了一件事：维护成本这东西，不能只看眼前那一眼的复杂度，要看它乘以使用时间之后的总量。纯静态站第一眼最轻，用久了最重；Nuxt 第一眼最重，用久了反而轻。想明白这一点，选型就不再纠结——你只不过是在决定，愿意现在多花一小时，还是未来多花一百小时。
