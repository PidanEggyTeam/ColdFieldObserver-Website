从上一次网站重构日志发布开始到现在，这个网站又被大规模地重构了一遍。如果上次那篇还算"在原有地基上翻新"，这一次就是把它整个掀掉重来：技术栈从 VitePress 换成了 Nuxt 4 + TypeScript + Tailwind CSS，版式从"顶栏+核心内容区域+双侧边栏"的 F 型布局，改成了"顶栏+核心内容区域+底栏"的 Z 型布局，连部署的地方都搬了家。跨度之大，接近于在超燃竞技场里中途换英雄——装备、技能、站位全部重配，还得保证对面看不出你在重建。

这篇文章我按五条线来写：技术栈、版式、部署、工具、零碎增强。每条线都说清楚三件事——改了什么、为什么改、过程中撞了什么。重构这件事，方案写在文档里总是漂亮的，真正决定成败的是那些文档不会写的细节。

## 一、技术栈重构

这次更换的核心提交，是十月二十五日合并的那次迁移：从 VitePress 换到 Nuxt 4 + @nuxt/content v3 + Nuxt UI 4 + TypeScript + Tailwind CSS v4，构建方式改为 SSG 静态生成。

为什么一定要换？因为原来的技术栈从根上就定位错了。VitePress 本质是一台文档生成器，它的设计目标是"把 Markdown 转成好看的文档站"，能力天花板从第一行代码就画好了：主题围绕文档目录组织，交互围绕页面跳转展开。而这个网站早就不是一个文档站——它有博客归档、分类标签、全文搜索、评论区、阅读进度、主题切换，还有一堆需要客户端状态的组件。继续用文档生成器硬撑，等于让一个纯辅助位的选手去打核心输出位：不是不能打，是每一次交锋都在对抗自己的装备，赢下来也全是勉强。

用竞技场的话说，这是一次换位：从辅助位换到法师位，整套装备跟着重配。新栈里每个部件各司其职，分工很清楚——Nuxt 4 提供完整的应用框架和路由能力，是骨架；@nuxt/content v3 接管 Markdown 内容库，负责把文章变成可查询的数据；Nuxt UI 4 负责组件层，顶栏、底栏、卡片、弹窗都从这里取；TypeScript 把类型安全钉死在编译期，让大部分低级错误在上线前就暴露；Tailwind CSS v4 用设计令牌统一视觉，颜色、间距、圆角不再靠手敲数值。

迁移不是一键完成的。中间还夹着一次版本升级：把 Nuxt 推到 4.6.3，同时移除了冗余的 Vue 依赖——因为 Vue 已经被 Nuxt 包含，单独声明只会带来版本错配的隐患。这类清理看着不起眼，却是迁移能不能长期稳定的关键。核心思路始终没变：静态产物的形态不变，能承载的上限变了。就像法师位的核心是"活得够久、输出够稳"，框架换了，但站点要交付的东西——一个能快速打开、能被搜索引擎读懂的静态站——一点没变。

## 二、样式和版式重构

技术栈换了，样式层自然全面接入 Nuxt UI 4。这不是把组件换一批那么简单，而是把整套视觉系统交给一套统一的设计语言来托管。以前颜色、间距、圆角散落在各个文件里，改一处要翻半天；现在收敛到 @theme 设计令牌，改一个变量，全站跟着变。

版式上的改动最直观。我从"顶栏+核心内容区域+双侧边栏"的 F 型布局，改成了"顶栏+核心内容区域+底栏"的 Z 型三段式。旧版在桌面端靠两侧边栏塞辅助信息，信息密度看着很高，实际是让读者在三条纵向通道之间来回切换视线——这也是后来我看到的那篇眼动研究里反复强调的点：人的视线根本不是"读"，是"扫"，三条通道只会把注意力撕碎。新版回到正常的文档流：顶栏常驻，内容居中，底栏收尾，视野只剩一条主通道，读起来才顺。

这套三段式的骨架不是我凭空想出来的，最先来自我自己的一个开源项目官网。那边走的是渐进路线：十月二十一日先把技术栈从文档生成器换成应用框架，隔了十天，到十月三十一日才在另一次提交里重构布局与样式、集成样式规范化，也就是换技术栈和换版式分作两步，中间隔着一段两套东西并存的日子。这个个人网站的做法不同——技术栈换完之后，接入 Nuxt UI 和换成三段式是在同一次提交里一起完成的，没有过渡态。

为什么不一样？借鉴骨架可以省掉从零试错的功夫，但推进节奏得按自己站点的情况定。那个开源项目官网历史包袱重、访问量也大，适合小步慢走，一次动一处；这个站内容结构简单，一次性切换反而干净，不用长期维护新旧两套样式并存的中间状态，也就少了一堆"两套规则打架"的隐患。战术上没有万能的打法，只有适配战场的打法——同一套骨架，落在不同规模的站点上，推进方式就该不一样。移动端的两个侧边栏原本都是抽屉菜单，各配一个按钮；三段式之后这套机制直接取消了，路由滚动也交还给浏览器，不再自建滚动容器——少一层封装，就少一类 bug。

这次同时删掉了大量冗余代码：左右侧栏、抽屉手势、阅读进度条、.site-main 滚动容器，以及成百上千行为了对抗旧框架而手写的样式。

这里有一个值得单独说的因果。之前那一版积攒了大量 bug，而其中相当一部分，病根就在旧版式本身——三条纵向通道、自建滚动容器、侧栏与抽屉的联动，几乎每一样都是问题的温床。为了把它们压下去，我前后写过一堆补丁代码：算滚动偏移的、手动同步抽屉状态的、修正容器高度的，越堆越多。换成三段式之后，这些结构的根基没了，之前出现的大量 bug 也随之得到解决；既然问题不再出现，那些专门为修它们而写的冗余代码也就一并删掉了。不是我逐个修好的，是结构一改，问题自己就不成立了。这跟竞技场里拆掉一个不合理的站位一个道理——把人挪到对的位置，比给错误站位写十套补救方案都管用。代码量和视觉复杂度是正相关的，砍掉一半冗余，页面反而更稳。首页重做为七个区块——Hero、关于我与身份主线、最新日志、长期维护的项目、游戏 ID 跑马灯、工具矩阵、关于站点；文章卡片统一成"封面+标题/分类·日期/摘要"，详情页去掉卡片外壳，正文直接落在页面底上。

细节上的打磨同样不少，随便举几处：

游戏 ID 跑马灯。这是这次重构才新加的区块，旧版里根本没有——它属于"完整应用"能力带来的东西，文档生成器做不出这种带状态的动态展示。既然是新的，就没有历史包袱，但第一版依然踩了坑：当时不管几张卡都套滚动组件，只有两个号时也左右循环，既看不清名字，又让整块变成一条空白跑道。于是改成按数量判断，超过五张才滚动，否则退回静止的横向列表，可键盘聚焦、可手动横滑。随后又放大卡片、把触发门槛降到三张，并让窄屏（小于 768px）退化成一行一张的静态网格，彻底消掉横向滚动条。

需要说明的是，前面这一连串调整都只是中间形态。从"无条件滚动"到"超过五张才滚"，再到"三张起滚、卡片放大、窄屏静态"，每一步都是拿真实数据喂出来的修正——号少的时候滚动反而碍事，号多的时候静态又放不下。而这一次落到"三张起滚、卡片放大到合适尺寸、窄屏静态网格"的这一版，在目前这个 ID 数量和屏幕分布下，是已经调到位、暂时不用再改的最终形态。它覆盖了从少到多、从宽屏到窄屏的几种情况，横向滚动条消失，信息也看得清。当然，"目前而言"四个字得留着——将来 ID 数量或展示需求变了，该调还得调，但现在没有再动它的理由。新功能上线后边跑边调，调到位就停手，不为改而改，这才是正确的节奏。

主题开关。方形图标按钮换成胶囊形态的三态开关，点击顺序固定为跟随系统→浅色→深色→循环。首帧先按跟随系统渲染，挂载后再切到真实模式，避免服务端和客户端渲染不一致。这类问题最阴的地方在于它不报错，只是首屏闪一下Theme切换的图标，队友还以为是你眼花了。

换版式后仍需单独处理的少数 bug。目录跳转原先会双重滚动、正文容器偏移，修成只在正文显式声明时才生成目录；顶部进度条因为品牌色变量没定义而透明，补上映射；Hero 底部的社交按钮像被一层渐变盖住，根因是网格底纹的遮罩作用到了所有后代元素，把绘制挪到伪元素上，淡出就只影响背景，内容恒定不透明；文章表格因为边框合并变成直角，改成四角圆角；标题去掉链接、只保留锚点，避免无障碍名称混进多余内容。此外还引入了 Preflight，补齐三套色阶与组件变量映射，并修掉正文站外链接点击后当前页跳走的问题——在构建期统一给外链加上新标签页打开，禁用 JS 时也照样生效。

这些都不是凭空新增的功能，而是把原本想要的效果，用更短、更稳的路径重新实现一遍。竞技场里管这叫"不亏血量换装备"——输出没变，容错高了。

## 三、网站部署迁移到 Cloudflare Workers

部署也换了个地方。之前是 GitHub Pages 外配 Cloudflare CDN 加速，现在一次性迁到 Cloudflare Workers。

先说旧方案的别扭之处。GitHub Pages 负责托管，Cloudflare 在外面套一层加速，这是两套系统叠在一起。要让静态站拿到理想的缓存策略和跨域行为，得在两边各配一遍，还得保证两边不打架。一旦牵涉自定义域名、HTTPS、404 回退，配置就会迅速复杂到没人敢动。

迁移后的形态干净得多：一个 assets-only Worker，静态资源直接托管在 Workers 上，自动处理 404 与 HTML 回退；生产与预览部署由 Cloudflare 连接 Git 后自动执行，每个分支都能拿到独立的 Worker Previews 地址——这点对调试特别有用，改版不用先合并就能看效果。GitHub 这边不再负责部署，只保留一条质量门禁：格式检查、lint、构建、产物校验，按顺序卡死，任何一环不过就别想往下走。本地构建仍可用 wrangler 兜底，不依赖线上环境。

构建链也一并重写：先 nuxi generate 生成静态页，再注入字体，最后跑产物断言。这里有个关键设置——nitro 预设锁死为 static，防止 Cloudflare 的环境变量擅自把预设切成带 Worker 入口的形态，那会让产物和部署方式对不上。旧的部署流水线文件、Pages 专属的权限与环境配置全部删除，文档同步改写部署章节。整个过程的目标只有一个：把"能跑起来"这件事，从依赖一堆外部配置，变成默认就成立。少配一层，就少一处会出错的地方。换基地不是为了换而换，是为了不再天天给旧基地打补丁。

## 四、网站工具的迁出

和部署迁移同步，站内工具也搬了家。

原先工具页和首页的工具矩阵都在本站内，其中还包括一个为游戏地图生成文案的小工具——输入地图名和地图码，按规则提取信息，输出普通版和短视频版两种文案。这类工具本质上需要不少客户端逻辑，把它塞在一个以内容为主的静态站里，等于让法师位去扛近战的活：能扛，但两边都别想发挥。

现在整套工具迁到独立的工具站 skystarlight.top，站内不再保留工具路由和工具清单，顶栏的"工具"改为指向外站。导航数据统一成 href + external 结构：外链新标签页打开、自动补上安全属性与角标、不参与当前路由高亮；顶栏、移动下拉、底栏三处共用同一份数据，改一处全站生效。首页那个工具矩阵区块也随之调整，订阅源并入社交链接统一渲染。

这是分工。主站专注内容，把文章写好、把阅读体验做顺；工具站专注功能，把交互做深。两边各自把一件事做到位，比一个站点什么都塞要清楚得多。竞技场里也是这个道理——远程输出和近战承伤硬塞给同一个角色，结果通常是两边都打不好。让专业的位置干专业的事，是最朴素也最容易被忽略的策略。

## 五、其他增强

除四条主线之外，还补了不少细节，逐个说清楚。

字体改为产物自包含。HarmonyOS Sans SC 的三档分片在构建期灌注进产物，代码字体交给 Vite 打包，不再从 CDN 侧加载。等于自带补给上场，不依赖地图上的补给站——断网、CDN 抖动、跨域拦截，都不再是正文掉字体的理由。字体这种东西平时没人注意，一旦掉了，整篇观感立刻垮掉，属于典型的"不出事就是零分，出了事扣十分"。

文章作者支持自定义。通过 frontmatter 指定，缺省时回退到站长。一篇文章署谁的名，本就该由文章自己说了算，而不是写死在模板里。这篇日志署的就是"蛋小蓝"。

构建期自动生成网站地图。以前站点有没有被搜索引擎完整收录，全凭运气——漏掉的页面连个提示都没有。现在每次构建自动生成站点地图，把文章、归档、分类、标签等路由一次性列全，搜索引擎照着抓就行。

产物校验。生成结束之后逐条对账：该渲染的页面有没有漏、静态预设对不对、字体有没有灌注到位。这一步解决的是一个很隐蔽的问题——"构建成功"不等于"没有漏页"，漏掉的页面在线上就是 404，而构建过程依然显示绿色。把校验放进流水线，等于在发布前多设了一道防线。

搜索弹窗换用现成组件。原先自建的搜索弹窗换成 Nuxt UI 的模态组件，开合动画与全站统一；顺手修掉了输入框出现两个清除按钮的问题。开发态还启用了框架自带的开发者工具，只在本地生效，生产构建不会打包进去。这些改动单独看都很小，但累积起来，决定的是日常用起来顺不顺手。

## 结语

从文档生成器到完整应用，从被两侧夹击的 F 型到一条主通道的 Z 型，从借来的托管到自己的基地，从自建工具到独立工具站——这次重构没有新增什么惊天动地的功能，做的其实是同一件事：把每一层放回它该在的位置。

我越来越确信，系统工程的价值不在某一个炫目的功能，而在所有环节对齐之后，那种"什么都不用想就能跑"的稳定。这比多写一个特性难得多，也值钱得多。功能可以后补，地基歪了却要推倒重来。这次我花了九天把地基重新浇了一遍，最大的收获不是修好了哪个 bug，而是发现一大批老 bug 根本不用修——换掉产生它们的版式，它们自己就消失了，连带那些为修补它们而堆的冗余代码一起清了个干净。下的功夫都在看不见的地方，但每一分，都会在最关键的时候兑现。下一次再有人问这个站为什么这么稳，答案不在某个巧妙的函数里，而在这些没人看得见的对账、校验和删掉的代码里。
